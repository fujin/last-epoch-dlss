Diagnostic behavior:
- Disabled unless the game process inherits LE_DLSS_DUMP_APP_PRESENT=1 and LE_DLSS_APP_PRESENT_DUMP_REQUEST points to an absolute marker filename in an existing directory.
- Marker is read-only and polled every60 application Presents. Creating it or changing its last-write timestamp requests one capture; at most2 attempts and2 images per process. No marker means no image capture. Use a fresh absent marker at launch to avoid capturing login/loading.
- The source is the actual D3D11 application swapchain texture selected by GetBuffer(index), exactly the resource copied into the existing D3D11-to-D3D12 FG path. Capture occurs before the hidden application Present, generated-frame presentation, backend overlay and desktop compositor. Game UI is included.
- CopyResource writes one staging resource. Later calls on the same immediate context use Map(DO_NOT_WAIT). No new hooks, explicit waits, flushes, device settings or render-state changes are introduced. Existing interop submission submits the copy. Device loss stops capture; failed/pending readbacks retain bounded resources. A pending copy after5 seconds, or an exception, disables further capture. An unremoved stalled device can retain its one staging texture/context/device until process exit.
- Output is raw top-down32-bit BI_RGB BMP. RGBA sources are channel-reordered to BGRA; alpha is255. RGB bytes are preserved without gamma conversion, tonemapping or Y flip. Only single-sample, single-mip, single-layer8-bit RGBA/BGRA resources up to8192x8192 are accepted; FP16 and10-bit HDR formats are refused.
- Filenames contain process, swapchain, backend app-frame and marker FILETIME. Log lines also record selected/fake index, source pointer, source QPC, source/readback call counters, format, RGB mean and RGB hash. Separately polled HUDless and application markers do not guarantee the same simulation frame. For comparison, use a stationary NR-off view, request HUDless first, then request the application image; compare static world regions, excluding UI and moving foliage.
- CPU conversion/hash/file writes can briefly stall the application during a capture. This build is for diagnosis, not performance measurement or normal use. Images/logs remain local beside the marker/normal log; nothing is uploaded.

Temporary installation from the mod project root, with the game stopped:
  & .\vendor\optiscaler-local\local-build-app-capture\Install-Diagnostic.ps1 -Mode Capture
After the short test and game exit:
  & .\vendor\optiscaler-local\local-build-app-capture\Install-Diagnostic.ps1 -Mode Restore
The helper supports -WhatIf and uses the existing deployment journal. It changes only version.dll, accepts only the exact journal-owned571C/A9F binary pair, and preserves normal stage/default backend selection. payload-capture/version.dll is the A9F diagnostic DLL; payload-restore/version.dll is exact571C. The payloads are local binaries, not source-repository content. Clear the diagnostic process environment variables after testing. Restoring571C disables this capture code regardless of environment.

Clean corresponding-source build:
Extract the pinned archive. From its OptiScaler-DLSS5-1.2.1 directory, set $env:GIT_CEILING_DIRECTORIES=(Split-Path -Parent (Get-Location).Path), then run git -c core.autocrlf=false apply --check <absolute-path-to-late-hudless.patch> and git -c core.autocrlf=false apply <absolute-path-to-late-hudless.patch>. Run powershell -ExecutionPolicy Bypass -File .\Build-Local.ps1 -BuildDirectoryName local-build-app-capture -ParallelProcesses 4. VS2022 C++ v143 Build Tools and Windows SDK are required. Build timestamps/toolchain versions affect the DLL hash; a rebuilt binary requires explicit new provenance and must not bypass the pinned deployment helper.
